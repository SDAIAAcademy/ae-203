# Answer key for trainers

The solution notebooks in this folder hold the reference code. This page lists, for each lab, what the data was built
to show (the planted problems) and the numbers the reference run produces, so a trainer can tell at a glance whether a
participant's result is right.

**Where the numbers come from.** Every number below comes from a run with `LLM_PROVIDER=scripted`. That provider is the
course's stand-in: a set of rules that behaves like a model, not a model. Labs 1.1, 1.4, 3.1 and 3.2 need no model, so
their numbers are real. On a hosted model, all other numbers will differ. The planted problems will still show up,
though not always in the same cases. Read a participant's numbers against the direction of the effect, not against the
exact figures.

The data is generated by `prepare_data.py` with seed 203. Today in the case is 15 November 2026.

## Common slips

- Using `\d` in a pattern: Python's `\d` also matches Arabic-Indic digits, so `B٢٧` passes a schema that expects
  `B27`.
- Comparing a Pydantic object with a dictionary: `model_dump(mode="json")` first, or dates never match.
- Calling the model inside a threshold sweep instead of once per question: six times the requests, and the free
  limits run out.
- Counting an unparsed grader reply as FAIL.
- Indexing normalised text but searching with a raw query.

## Capstone

The three cases and the rubric are in `labs/capstone/README.md`. The starter's evaluation reproduces Lab 4.1 on the 40
golden cases (extraction 15 of 15, tool use 10 of 10, grounded 10 of 15) and its five tests pass offline. In the
defence, a good new case to add is one from a language or a policy the participant's set does not cover yet. For
example, an Arabizi lost-item message for case B, or a cancelled trip on the day of a planned closure (P20) for case C.
