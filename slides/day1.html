The unit of everything

A model reads and writes tokens, and you pay per token

  • A token is a piece of text from the model's vocabulary: a word, part of a word, a digit, a space.
  • Input tokens (what you send) and output tokens (what it writes) are counted and usually priced apart.
  • The context window is the most tokens one call can hold, input and output together.
  • Each model family has its own tokenizer, so the same text has a different count on each.

From tokens to money

Daily cost is messages times tokens times price, per million

def daily_cost(n, tokens_in, tokens_out, price_in, price_out):
    return n * (tokens_in * price_in + tokens_out * price_out) / 1_000_000

daily_cost(10_000, 490, 60, 0.10, 0.40)    # 0.73 a day
daily_cost(10_000, 490, 60, 3.00, 15.00)   # 23.7 a day
Example prices, not a provider's. The two price pairs are inputs to compute with. Take real ones from the pricing page on the day you decide.

The lab uses two example price pairs per million tokens to show that the price list changes the answer by more than an order of magnitude while the tokens stay the same. Free hosted models cost nothing in money but have request limits per minute and per day; the OpenRouter limits page states them. Cost per 1,000 requests, which the capstone reports, is the daily cost divided by ten here.

Sources: OpenRouter API rate limits page.

Three ways to say the same thing

Three API shapes carry the same conversation in different places

Chat Completions

A list of messages with roles: system, user, assistant, tool. The most widely copied shape.

Responses

Instructions plus input items; the reply is a list of output items such as messages and function calls.

Messages

A top-level system field; content is a list of typed blocks such as text, tool use and tool result.

Open Responses is an open specification, based on the Responses shape, for one interface across providers.

Chat Completions and Responses are documented by OpenAI; Messages is Anthropic's shape. Many providers and local servers serve Chat Completions, which is why the course client speaks it. The Open Responses project describes itself as an open-source specification for multi-provider interfaces based on the Responses API.

Sources: OpenAI API reference for Chat Completions and Responses; Anthropic Messages API reference; openresponses.org.

Who says what

Instructions come from Darb; the message comes from the rider

System: You are Wasil, the rider assistant of Darb Transit Authority. Today is 2026-11-15. Never promise a refund. User: The 27 bus was 22 minutes late yesterday. I want a refund.
Darb's instructionsThe rider's words
  • The system message holds what is true for every rider: identity, rules, the date.
  • The user message holds only what this rider wrote. Never paste rider text into the instructions.

The separation is not a security boundary: a model can still follow instructions written in the user's text (Day 4). It is a clarity boundary: it keeps the authority's rules in one reviewed place and makes the rider's words data.

Never wait forever

Every model call needs a timeout shorter than the rider's patience

  • A call without a timeout ties up a worker until the provider gives up, if it ever does.
  • Set it from your latency budget: Wasil's reply should start within a few seconds.
  • A timeout is a failure you chose: decide what happens next, retry or fall back.
The client's default may be long. The OpenAI Python client takes a timeout argument; the course client passes one on every call.

llm.client() passes timeout and max_retries explicitly so nobody relies on a library default. Ask what Wasil should tell a rider after a timeout: that the answer is delayed and a ticket can be opened, not silence.

The 401 row is the one every participant meets: a key pasted with a space, or a revoked key. Retrying a 401 only burns time; the fix is in the configuration. The lab's tests cover the 400 the same way: one attempt, no fallback.

How long to wait

Wait longer after each failure, with a little randomness

for attempt in range(retries + 1):
    try:
        return endpoint(prompt, timeout=timeout)
    except TimeoutError: ...
    except EndpointError as e:
        if e.status not in RETRYABLE:
            raise                      # a 400 is not retried
    time.sleep(base * 2 ** attempt + random.uniform(0, base))
Jitter keeps clients that failed together from retrying together.

In the lab's run: a timeout, then a 429, then an answer on the third attempt. Exponential backoff gives the provider room; jitter spreads the retries. A provider's Retry-After header, when present, beats your own guess.
