Session 1

Schemas for model output

  • Write a schema whose constraints catch wrong values

01
Why a schema

A ticket service needs fields, not a paragraph

Riderel bas 27 ta2a5ar ams, abi refund
Wasil reads{"route": "B27", "date": "2026-11-14", "complaint_type": "delay", "refund_requested": true}
  • Every field has a type and a list of allowed values.
  • The service downstream trusts the fields because code checked them.
  • What the schema cannot express (does route B27 exist?) is checked by the service.

The rider wrote in Arabizi, with "ams" for yesterday and no date. The extraction must resolve "yesterday" from the day the message was received; that is why the system prompt carries the received date. Ask: which field would you least trust from a model? Most rooms say the date, and Lab 2.1 agrees.

Lab 2.1 · step 1

A typed model in code is the schema, the validator and the documentation

class RiderMessage(BaseModel):
    route: str | None = Field(default=None, pattern=r"^(M[1-4]|B[0-9]{2})$")
    date: dt.date | None = None
    complaint_type: Literal["delay", "cancellation", "overcharge", "lost_item",
                            "accessibility", "staff", "cleanliness", "other"]
    refund_requested: bool
One definition, three uses. model_json_schema() goes to the model, model_validate_json() checks its reply, and the code reads typed fields.

Pydantic is the course's example; Instructor wraps the same idea around model calls, Outlines constrains decoding to a schema. Optional fields matter: a message that names no route must be allowed to say so, or the schema pushes the model to invent one.

Sources: Pydantic JSON Schema documentation.

Measured in Lab 2.1

A route pattern written with \d accepts Arabic-Indic digits

Pattern"B27""B٢٧"
^B\d{2}$validvalid
^B[0-9]{2}$validrejected
The trip-status service knows only B27. With \d the wrong value passes validation and fails later, far from its cause.

Run in the lab with Pydantic: its pattern engine counts every Unicode decimal digit as \d. Arabic riders write Arabic-Indic digits all the time (MSG-003 says "الحافلة ١٠"). The stricter pattern turns a silent failure into a repair the model can make.

Getting valid output

Constrain the decoding, or validate and retry: production does both

Constrained decoding

The provider only lets the model produce tokens that fit the schema (a JSON Schema response format with strict mode, or a library such as Outlines on a local model).

Validate and retry

Ask, validate in your code, send the errors back. Works with every model, costs extra calls.

Not every free model or gateway enforces the schema. Validate anyway: a schema cannot say "a date this month" or "a route that exists".

OpenRouter documents structured outputs with a JSON Schema response format and lists which models support it; support varies by model and changes. The stretch of Lab 2.1 sets strict mode; the scripted stand-in ignores it, so only a run with a key says whether the provider enforced it.

Sources: OpenRouter structured outputs guide.

03
Tool calling

The model asks; your code decides, runs and answers

1 · Definename, description, typed parameters
→
2 · Callthe model replies with a tool call, not text
→
3 · Executevalidate, run, catch errors
→
4 · Returnthe result as a tool message
The model never touches the service. Every call passes through code you wrote and tested.

Draw the loop on the board: steps 2 to 4 repeat until the model answers in text. The result goes back with the tool call's id so the model knows which call it answers. Yesterday's comparison table showed where each shape puts these pieces.

Lab 2.3 · step 1

The description tells the model when to call; the schema tells it how

{"type": "function", "function": {
    "name": "get_trip_status",
    "description": "Status of one route on one service day: delay in minutes, "
                   "cancelled trips and the reason. Use it whenever a rider asks "
                   "whether a trip was late or cancelled.",
    "parameters": StatusArgs.model_json_schema()}}

The same Pydantic model that validates the arguments generates the parameters: one definition, no drift. Descriptions are tokens on every call (406 tokens for Wasil's two tools on Day 1), so make every word earn its place.

When the service fails

A tool error or a timeout goes back to the model, which tells the rider

RiderWas bus 99 late yesterday?
WasilI could not find that route. Darb runs metro lines M1 to M4 and bus routes B10 to B60; which one did you take?
RiderWas bus 33 late yesterday?
WasilI could not reach the trip-status service just now. I have noted your message and a staff member will follow up.

B33's feed is slow by design (1.5 seconds against a 0.5-second timeout in the lab). The call runs in a thread with a timeout so the conversation never hangs. An exception would end the conversation with nothing for the rider; a tool result lets the model explain.

Session 4

Workflow or agent

  • Write a task as a fixed workflow of model and tool steps
  • Write the same task as a model-driven tool loop
  • Choose between them from measured steps, cost and failures
04
Who decides the next step?

In a workflow your code decides; in a tool loop the model does

Fixed workflow

Extract, look up the status, open a ticket, reply. The model reads the message; code runs the steps in order.

Tool loop

The model gets both tools and chooses what to call and when to stop, within a step budget.

The question is not which is modern. It is whether the steps depend on what the tools return.

Many production "agents" are workflows with one or two model steps, and that is a feature. Ask the room for a Darb task whose steps cannot be written in advance: a rider whose message mixes a lost item and a delay on two routes might be one.

Lab 2.4 · step 1

The workflow is ordinary code with one model call in it

obj, _, _ = wasil.extract(m["text"], m["received"])        # model
if obj is None:
    return {"ticket": None, "reply": "a member of staff will read it"}
status = svc.call_tool("get_trip_status", {...})              # code
ticket = svc.call_tool("create_ticket", {..., "summary":
            f"Rider reports {obj.complaint_type} on {obj.route}; {said}"})
return {"ticket": ticket_id, "reply": f"I opened ticket {ticket_id}; {said}."}

Every step after the extraction is testable without a model. The reply is written by code, so it never promises a refund. The price: a rider whose case does not fit the steps gets a ticket anyway, which is often the right default.

Lab 2.4 · step 2

The loop reaches the same ticket in three model calls instead of one

ridermetro M3 ta2a5ar 12 da2i2a yom 10 november
model 1get_trip_status(route="M3", date="2026-11-10")
model 2create_ticket(category="delay", route="M3", ...)
model 3On 2026-11-10, M3 ran 12 minutes late (vehicle breakdown). I opened ticket DT-1001.

Each model call resends the instructions, both tool definitions and the growing conversation, which is why the tokens grow faster than the calls. Point at the final text: the model wrote it, so the output checks of Day 4 must read it.

The stretch, and a principle

A rule written in a policy is code, not a judgement for the model

def eligible(route, delay):
    return delay >= (15 if route.startswith("M") else 25)

Code applies it

Same answer every time, testable, auditable.

The model explains it

In the rider's language, citing P03 (Day 3).

Of the ten cases, three were eligible (B27 and B21 at 25 minutes, B60 at 30). Note that Wasil still never approves a refund: P25 says staff decide; the flag only helps them. Mixing the two roles is how assistants end up promising money.
