02
One model grader

Some properties need a reader: is every claim in the answer supported by its passage?

Code can check

The citation exists, the number appears, the JSON is valid, the answer abstained.

A reader is needed for

An answer that adds "you also get a free day pass" to a passage that never said so.

A grader is a model too, with its own errors. Measure it before you trust its numbers.

The order of preference: code checks first, a model grader only for what code cannot see, and people for the labels that check the grader. Ask: who reads the grader's mistakes?

Lab 4.2 · steps 1 and 2

One binary question, defined, with a verdict code can parse

You are a strict grader of faithfulness. An answer is faithful when every claim
and every number in it appears in the passage. Anything the passage does not
state, even if true elsewhere, makes it unfaithful. Reply with one JSON object
and nothing else: {"verdict": "PASS" or "FAIL", "reason": "one sentence"}.
Unparsed is not FAIL. Count replies that cannot be parsed separately; never guess them.

Binary beats a 1 to 10 scale: easier to define, to label and to agree on. The reason field is for the humans reading disagreements, not for the score. Ask why "even if true elsewhere" is in the prompt: graders often pass an answer that is correct in the world but not supported by the passage.

The kind of fault lets you see which errors the grader catches, not only how many. In a real team, two people label independently and settle disagreements first; their own agreement is the ceiling a grader can reach.

Lab 4.2 · step 3

Kappa gives no credit for agreement that chance alone would reach

A grader that always says PASS

Agrees on the 18 faithful answers: agreement 0.60, kappa 0.

The formula

kappa = (p_o - p_e) / (1 - p_e), where p_e is the chance both say PASS plus the chance both say FAIL.

Darb's rule, set before the run: trust the grader when agreement is at least 0.85 and kappa at least 0.6.

Work the always-PASS example on the board: p_o = 18/30 = 0.6; the grader says PASS every time and the labels say PASS 60% of the time, so p_e = 0.6 × 1 + 0.4 × 0 = 0.6, and kappa = 0. The thresholds are a team decision, written before the run so nobody moves them after seeing the result.

04
Packaging the assistant as a service

Two endpoints, typed at the door

@app.get("/health")
def health():
    return {"status": "ok", "provider": llm.PROVIDER,
            "model": llm.MODEL}

@app.post("/ask", response_model=Reply)
def ask(req: Ask) -> Reply:
    out = w.answer(req.text, req.received)
    return Reply(answer=out["answer"], ...)

Ask

text of 1 to 2,000 characters; an optional date. An empty message gets 422 before any model call.

Reply

answer, kind, citations, abstained, flags, and the AI disclosure. Never the input.

FastAPI with Pydantic models: the same validation participants used on model output on Day 2, now on the request. The health check never calls the model: a probe every few seconds would cost calls and count against the rate limit.

The handler written by hand raises on the bad body (a decode error, then a missing key), and an unhandled exception becomes a 500. The typed handler lets the framework parse and validate first. Lab 4.4 checks the same on Wasil's own app: a body that is not JSON gets 422 and never reaches the model.

The status is an instruction to the client

A 4xx says "fix your request"; a 5xx says "our fault, try again"

4xx: the request is wrong

The client fixes the body and does not retry it as it is. 400 covers malformed syntax, 422 well-formed content the server cannot accept; FastAPI answers 422 for both and tells them apart by type. The reply names the problem.

5xx: the server failed

The client's retry loop from Day 1 sends the same broken body again, and whoever runs the service is alerted for a fault that is the client's.

A 500 for a bad body costs twice: retries that can never pass, and an alert that points at the wrong team.

HTTP defines the 4xx class as the client seeming to have erred, and asks the server to explain the error and whether it is temporary or permanent. A parallel case: Darb's app sends the received date as "15/11/2026"; the date pattern on Ask refuses it with 422 and names the field received, and the app team fixes the format. Ziyad's alerts should fire on 5xx, never on 4xx alone.

Sources: RFC 9110 HTTP Semantics; FastAPI testing.
